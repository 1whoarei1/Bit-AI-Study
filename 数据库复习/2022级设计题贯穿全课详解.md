# 2022 级图书馆设计题贯穿全课详解

> 目标：用 2022 级设计题串起数据库原理课程的整体思路。本文既给出考试可写答案，也解释每一步背后的课程知识点。

## 0. 题目重述与做题路线

题目要求建立图书馆管理数据库系统，已知语义：

1. 图书馆可以馆藏多个出版社的多种书籍，需要管理出版社信息。
2. 需要管理书籍信息；同一种书可以馆藏多本，并能追踪每本书的借阅情况。
3. 需要管理读者信息；每位读者有可借阅图书数量限制。
4. 查询服务包括：
   - 查询到期图书名称以及读者电子邮件地址。
   - 查询馆藏图书种类最多的出版社名称、地址、城市。
   - 查询借阅过某作者编写的所有书籍的读者姓名。
5. 要求：
   - 设计 E-R 图并给出属性。
   - 转为符合 3NF 的关系模型，指出主码。
   - 用 SQL 创建书籍表、读者表。
   - 建立出版社在北京的所有书籍的视图。

做题路线：

```text
现实业务需求
  -> 概念结构设计：E-R 模型
  -> 逻辑结构设计：关系模型
  -> 规范化检查：3NF
  -> SQL 实施：CREATE TABLE / CREATE VIEW
  -> 查询与运行：关系代数、查询优化、完整性、安全、事务并发恢复
```

这正好对应课程主线：数据库系统引论 -> 数据模型 -> 关系数据库 -> SQL -> 查询优化 -> 安全完整性 -> 恢复并发 -> 规范化理论 -> 数据库设计。

## 1. 需求分析：先把自然语言变成数据语义

### 1.1 本阶段在课程中的位置

数据库设计通常分为：

1. 需求分析。
2. 概念结构设计。
3. 逻辑结构设计。
4. 物理结构设计。
5. 数据库实施。
6. 运行和维护。

本题给出的自然语言就是需求分析材料。需求分析要回答：

- 系统要管理哪些对象？
- 对象有哪些属性？
- 对象之间有什么联系？
- 系统未来要支持哪些查询和业务规则？

### 1.2 从题面提取对象

题面直接出现的名词：

- 出版社。
- 书籍。
- 每本书，也就是同一种书的具体馆藏副本。
- 读者。
- 借阅情况。

为什么要区分“书籍”和“每本书”？

这是本题最关键的语义点。“数据库原理”这本书是一种书，图书馆可能有 5 本馆藏副本。每本副本有自己的条码、状态、借阅记录。若只设计 `Book`，就无法追踪“第几本书被谁借走”。所以需要：

- `Book`：书目层面，表示一种书。
- `BookCopy`：馆藏副本层面，表示一本具体可借的书。

### 1.3 从查询倒推必须保留的属性

查询服务会反推属性需求：

| 查询 | 必须有的数据 |
|---|---|
| 到期图书名称和读者电子邮件 | 书名、读者邮箱、借阅到期日期、归还日期 |
| 馆藏图书种类最多的出版社 | 出版社名称、地址、城市、书籍和出版社的对应关系 |
| 借阅过某作者编写的所有书籍的读者姓名 | 作者、书籍、具体副本、借阅记录、读者姓名 |

所以即使题面没逐项列属性，答案也应包含 `Email`、`DueDate`、`ReturnDate`、`Author` 等。

## 2. 第一问：设计 E-R 图

### 2.1 什么是 E-R 图

E-R 图是实体-联系图，是概念模型最常用的表示方法。

课程位置：

- 数据模型分为概念模型、逻辑模型、物理模型。
- 概念模型面向用户和现实世界，独立于 DBMS。
- E-R 图就是概念模型的典型工具。

E-R 图基本元素：

| 元素 | 图形 | 含义 |
|---|---|---|
| 实体 | 矩形 | 现实中可区分的对象，如读者、书籍 |
| 属性 | 椭圆 | 实体或联系具有的特征，如姓名、邮箱 |
| 联系 | 菱形 | 实体之间的关联，如出版、借阅 |
| 码 | 属性下划线 | 唯一标识实体的属性 |
| 联系类型 | 1:1、1:n、m:n | 实体之间的数量约束 |

考试没有画图工具时，可以用“实体 + 属性 + 联系类型”的文字形式替代 E-R 图，只要语义清楚。

### 2.2 本题实体设计

建议实体如下：

```text
出版社 Publisher(
  出版社编号 PubID,
  出版社名称 PubName,
  地址 Address,
  城市 City
)

书籍 Book(
  书籍编号 BookID,
  书名 Title,
  作者 Author,
  出版年份 PubYear,
  出版社编号 PubID
)

馆藏副本 BookCopy(
  副本编号 CopyID,
  书籍编号 BookID,
  馆藏状态 Status,
  入馆日期 InDate
)

读者 Reader(
  读者编号 ReaderID,
  姓名 ReaderName,
  电子邮件 Email,
  可借数量上限 MaxBorrow
)

借阅 Borrow(
  借阅编号 BorrowID,
  读者编号 ReaderID,
  副本编号 CopyID,
  借出日期 BorrowDate,
  到期日期 DueDate,
  归还日期 ReturnDate
)
```

说明：

- `Publisher`、`Book`、`BookCopy`、`Reader` 是实体。
- `Borrow` 可看作读者和馆藏副本之间的联系，也可在转关系模型时设计为独立关系。
- `BorrowID` 不是题目强制要求，但实际设计中方便标识每一次借阅事件。考试也可以用 `(ReaderID, CopyID, BorrowDate)` 作为主码。

### 2.3 本题联系设计

```text
Publisher 1:n Book
含义：一个出版社可出版多种书；一种书属于一个出版社。

Book 1:n BookCopy
含义：一种书可有多本馆藏副本；一本副本只对应一种书。

Reader m:n BookCopy，通过 Borrow 联系实现
含义：一个读者可借多本副本；一本副本在不同时间可被不同读者借阅。
联系属性：BorrowDate, DueDate, ReturnDate。
```

文字版 E-R 图：

```text
[Publisher] 1 ----- n [Book] 1 ----- n [BookCopy]
                                       |
                                       | n
                                  [Borrow]
                                       | n
                                   [Reader]
```

更准确地说，`Reader` 和 `BookCopy` 是 m:n 联系，但一次借阅联系发生在一个读者和一个副本之间，并带有借出日期、到期日期、归还日期。

### 2.4 为什么查询服务会影响 E-R 图

如果没有“查询借阅过某作者编写的所有书籍的读者姓名”，也许我们会漏掉 `Author`。如果没有“到期图书名称以及读者电子邮件”，也许会漏掉 `Email`、`DueDate`、`ReturnDate`。

数据库设计不是只照抄名词，而是要结合未来操作来建模。这对应课程中的：

- 数据库系统面向共享应用。
- 数据库设计需要综合数据需求和处理需求。
- 数据库不是孤立表格，而是服务查询、更新和约束的系统。

## 3. 第二问：E-R 图转换为关系模型，并满足 3NF

### 3.1 什么是关系模型

关系模型是用二维表表示数据和数据联系的逻辑数据模型。

关系模型中的基本概念：

- 关系：二维表。
- 元组：表中的一行。
- 属性：表中的一列。
- 域：属性取值范围。
- 主码：唯一标识元组的属性或属性组。
- 外码：引用其他关系主码的属性或属性组。

题目要求“转换为关系模型”，就是把 E-R 图中的实体、属性、联系转换成一组关系模式。

### 3.2 顺便比较其他数据模型

本题最终选择关系模型，因为现代数据库课程主要围绕关系数据库。

其他模型：

- 层次模型：用树表示数据，适合 1:n，但表达 m:n 不方便。
- 网状模型：可表达复杂联系，但结构和 DML/DDL 复杂。
- 面向对象模型：适合复杂对象，但不是本课程期末主线。
- 关系模型：结构简单、理论基础好、SQL 标准成熟，是考试核心。

本题中的 `Reader m:n BookCopy` 若用层次模型会很别扭，而关系模型可以用 `Borrow` 中间关系自然表达。

### 3.3 E-R 到关系模型的转换规则

考试必须会写：

1. 实体型 -> 一个关系模式，实体属性 -> 关系属性，实体码 -> 主码。
2. 1:n 联系 -> 在 n 端加入 1 端主码作为外码。
3. m:n 联系 -> 新建一个关系模式，包含两端主码和联系属性。
4. 1:1 联系 -> 可并入任一端，也可单独建表。
5. 多元联系 -> 新建关系模式，包含参与实体主码和联系属性。

### 3.4 本题关系模式答案

推荐答案：

```text
Publisher(
  PubID,
  PubName,
  Address,
  City
)
主码：PubID

Book(
  BookID,
  Title,
  Author,
  PubYear,
  PubID
)
主码：BookID
外码：PubID -> Publisher(PubID)

BookCopy(
  CopyID,
  BookID,
  Status,
  InDate
)
主码：CopyID
外码：BookID -> Book(BookID)

Reader(
  ReaderID,
  ReaderName,
  Email,
  MaxBorrow
)
主码：ReaderID

Borrow(
  BorrowID,
  ReaderID,
  CopyID,
  BorrowDate,
  DueDate,
  ReturnDate
)
主码：BorrowID
外码：ReaderID -> Reader(ReaderID)
外码：CopyID -> BookCopy(CopyID)
```

若不想引入 `BorrowID`，也可以：

```text
Borrow(
  ReaderID,
  CopyID,
  BorrowDate,
  DueDate,
  ReturnDate
)
主码：(ReaderID, CopyID, BorrowDate)
```

考试中两种都可以，但引入 `BorrowID` 更利于后续扩展。

### 3.5 为什么这组关系符合 3NF

这一步对应“关系数据库设计理论”章节。

先回顾范式：

- 1NF：属性值不可再分。
- 2NF：非主属性完全依赖于候选码，消除部分依赖。
- 3NF：非主属性不传递依赖于候选码，消除传递依赖。
- BCNF：每个非平凡函数依赖的决定因素都是候选码或超码。

逐表看：

```text
Publisher(PubID, PubName, Address, City)
函数依赖：PubID -> PubName, Address, City
PubID 是主码，非主属性都直接依赖主码，符合 3NF。

Book(BookID, Title, Author, PubYear, PubID)
函数依赖：BookID -> Title, Author, PubYear, PubID
BookID 是主码，非主属性直接依赖主码，符合 3NF。

BookCopy(CopyID, BookID, Status, InDate)
函数依赖：CopyID -> BookID, Status, InDate
CopyID 是主码，符合 3NF。

Reader(ReaderID, ReaderName, Email, MaxBorrow)
函数依赖：ReaderID -> ReaderName, Email, MaxBorrow
ReaderID 是主码，符合 3NF。

Borrow(BorrowID, ReaderID, CopyID, BorrowDate, DueDate, ReturnDate)
函数依赖：BorrowID -> ReaderID, CopyID, BorrowDate, DueDate, ReturnDate
BorrowID 是主码，符合 3NF。
```

为什么不要把所有信息放进一张大表？

假设设计成：

```text
BorrowAll(
  ReaderID, ReaderName, Email, MaxBorrow,
  CopyID, BookID, Title, Author,
  PubID, PubName, Address, City,
  BorrowDate, DueDate, ReturnDate
)
```

会出现：

- 数据冗余：同一出版社信息重复出现。
- 更新异常：出版社地址变化要改很多行。
- 插入异常：没有书籍时无法单独插入出版社。
- 删除异常：删除最后一本书可能丢失出版社信息。

这些正是规范化理论要解决的问题。

### 3.6 主码、外码与完整性约束的联系

这一步连接“关系完整性”章节。

- 实体完整性：主码不能为空，例如 `ReaderID`、`BookID` 不得为空。
- 参照完整性：外码必须引用已存在的主码，例如 `Book.PubID` 必须存在于 `Publisher.PubID`。
- 用户定义完整性：`MaxBorrow >= 0`，`DueDate >= BorrowDate`，`ReturnDate` 可为空。

注意：

- 外码不必和被参照主码同名，只要语义和类型匹配。
- 同一关系内部也可以有参照约束，但本题主要是关系之间的外码。

## 4. 第三问：用 SQL 创建书籍表、读者表

### 4.1 SQL 在课程中的位置

SQL 是关系数据库标准语言，集数据定义、数据查询、数据操纵、数据控制于一体。

常见功能：

- DDL：`CREATE TABLE`、`ALTER TABLE`、`DROP TABLE`。
- DML：`SELECT`、`INSERT`、`UPDATE`、`DELETE`。
- DCL：`GRANT`、`REVOKE`。
- 视图：`CREATE VIEW`。

本题第三问是 DDL。

### 4.2 建表前的依赖顺序

如果 `Book` 中有 `PubID` 外码引用 `Publisher`，实际建表时应先建 `Publisher`，再建 `Book`。题目只要求书籍表、读者表，但为了外码完整，考试可以只写 `Book` 和 `Reader`，并注明 `Publisher` 已存在；更完整则先补 `Publisher`。

### 4.3 SQL 答案

```sql
CREATE TABLE Publisher (
  PubID CHAR(10) PRIMARY KEY,
  PubName VARCHAR(100) NOT NULL,
  Address VARCHAR(200),
  City VARCHAR(50)
);

CREATE TABLE Book (
  BookID CHAR(20) PRIMARY KEY,
  Title VARCHAR(200) NOT NULL,
  Author VARCHAR(100),
  PubYear INT,
  PubID CHAR(10),
  FOREIGN KEY (PubID) REFERENCES Publisher(PubID)
);

CREATE TABLE Reader (
  ReaderID CHAR(20) PRIMARY KEY,
  ReaderName VARCHAR(80) NOT NULL,
  Email VARCHAR(120),
  MaxBorrow INT NOT NULL CHECK (MaxBorrow >= 0)
);
```

若考试只要求“书籍表、读者表”，可写：

```sql
CREATE TABLE Book (
  BookID CHAR(20) PRIMARY KEY,
  Title VARCHAR(200) NOT NULL,
  Author VARCHAR(100),
  PubYear INT,
  PubID CHAR(10)
);

CREATE TABLE Reader (
  ReaderID CHAR(20) PRIMARY KEY,
  ReaderName VARCHAR(80) NOT NULL,
  Email VARCHAR(120),
  MaxBorrow INT CHECK (MaxBorrow >= 0)
);
```

### 4.4 这段 SQL 体现了哪些知识点

1. 关系模型：每个表对应一个关系模式。
2. 实体完整性：`PRIMARY KEY` 保证主码唯一且非空。
3. 参照完整性：`FOREIGN KEY` 保证出版社编号有效。
4. 用户定义完整性：`CHECK (MaxBorrow >= 0)`。
5. 数据类型与域：`CHAR`、`VARCHAR`、`INT` 规定属性取值域。
6. 数据库实施：把逻辑模型落地为 DBMS 可执行的 DDL。

## 5. 第四问：建立出版社在北京的所有书籍视图

### 5.1 什么是视图

视图是从一个或多个基本表导出的虚表，是外模式的一种实现方式。

视图的作用：

- 简化用户查询。
- 提供安全保护，让用户只看到部分数据。
- 提高数据逻辑独立性。

视图通常不真正存储数据，只保存定义；查询视图时 DBMS 根据视图定义去查询基本表。

### 5.2 SQL 答案

```sql
CREATE VIEW BeijingPublisherBooks AS
SELECT B.BookID, B.Title, B.Author, B.PubYear, P.PubName
FROM Book B
JOIN Publisher P ON B.PubID = P.PubID
WHERE P.City = '北京';
```

如果想展示出版社地址：

```sql
CREATE VIEW BeijingPublisherBooks AS
SELECT B.BookID, B.Title, B.Author, B.PubYear,
       P.PubName, P.Address, P.City
FROM Book B
JOIN Publisher P ON B.PubID = P.PubID
WHERE P.City = '北京';
```

### 5.3 视图与安全性的联系

如果只授权普通用户查询这个视图：

```sql
GRANT SELECT ON BeijingPublisherBooks TO user1;
```

用户只能看到北京出版社书籍信息，看不到读者邮箱、借阅记录等敏感信息。这体现：

- 数据库安全性。
- 自主存取控制 DAC。
- `GRANT` 授权机制。

若允许用户继续转授权：

```sql
GRANT SELECT ON BeijingPublisherBooks TO user1 WITH GRANT OPTION;
```

## 6. 用本题查询服务串联关系代数、SQL 和查询优化

题目没有要求写这些查询，但题面给了查询服务。复习时可以用它们把关系代数、SQL 和优化串起来。

### 6.1 查询到期图书名称和读者邮箱

SQL：

```sql
SELECT B.Title, R.Email
FROM Borrow Bo
JOIN Reader R ON Bo.ReaderID = R.ReaderID
JOIN BookCopy C ON Bo.CopyID = C.CopyID
JOIN Book B ON C.BookID = B.BookID
WHERE Bo.ReturnDate IS NULL
  AND Bo.DueDate < CURRENT_DATE;
```

关系代数：

```text
Π_Title, Email (
  σ_ReturnDate IS NULL ∧ DueDate < CURRENT_DATE
  (Borrow ⋈ Reader ⋈ BookCopy ⋈ Book)
)
```

优化后的思路：

```text
先选择未归还且已到期的 Borrow，
再与 Reader、BookCopy、Book 连接，
最后投影 Title 和 Email。
```

这体现查询优化的基本原则：选择先做、投影提前、减少中间结果。

### 6.2 查询馆藏图书种类最多的出版社

这里“种类”通常指 `Book` 中不同书籍种类，不是 `BookCopy` 的副本数。

SQL：

```sql
SELECT P.PubName, P.Address, P.City
FROM Publisher P
JOIN Book B ON P.PubID = B.PubID
GROUP BY P.PubID, P.PubName, P.Address, P.City
HAVING COUNT(*) >= ALL (
  SELECT COUNT(*)
  FROM Book
  GROUP BY PubID
);
```

或使用排序取第一名：

```sql
SELECT P.PubName, P.Address, P.City
FROM Publisher P
JOIN Book B ON P.PubID = B.PubID
GROUP BY P.PubID, P.PubName, P.Address, P.City
ORDER BY COUNT(*) DESC;
```

考试若 DBMS 不支持 `LIMIT`，第一种更标准。

知识点：

- `GROUP BY` 对出版社分组。
- `COUNT(*)` 统计书籍种类。
- `HAVING` 筛选分组。
- `WHERE` 筛记录，`HAVING` 筛分组。

### 6.3 查询借阅过某作者编写的所有书籍的读者姓名

这是典型“除法”语义：读者借过某作者的全部书籍。

SQL 写法一：双重 `NOT EXISTS`

```sql
SELECT R.ReaderName
FROM Reader R
WHERE NOT EXISTS (
  SELECT 1
  FROM Book B
  WHERE B.Author = '某作者'
    AND NOT EXISTS (
      SELECT 1
      FROM Borrow Bo
      JOIN BookCopy C ON Bo.CopyID = C.CopyID
      WHERE Bo.ReaderID = R.ReaderID
        AND C.BookID = B.BookID
    )
);
```

SQL 写法二：分组计数

```sql
SELECT R.ReaderName
FROM Reader R
JOIN Borrow Bo ON R.ReaderID = Bo.ReaderID
JOIN BookCopy C ON Bo.CopyID = C.CopyID
JOIN Book B ON C.BookID = B.BookID
WHERE B.Author = '某作者'
GROUP BY R.ReaderID, R.ReaderName
HAVING COUNT(DISTINCT B.BookID) = (
  SELECT COUNT(*)
  FROM Book
  WHERE Author = '某作者'
);
```

关系代数除法思路：

```text
ReaderBorrowBook(ReaderID, BookID)
  = Π_ReaderID, BookID(Borrow ⋈ BookCopy)

AuthorBooks(BookID)
  = Π_BookID(σ_Author='某作者'(Book))

借过该作者所有书的读者编号
  = ReaderBorrowBook ÷ AuthorBooks
```

再与 `Reader` 连接取姓名：

```text
Π_ReaderName((ReaderBorrowBook ÷ AuthorBooks) ⋈ Reader)
```

这串起了：

- 关系代数中的除运算。
- SQL 中 `NOT EXISTS` 和 `GROUP BY HAVING` 的等价表达。
- 查询优化中连接与投影的提前。

## 7. 用本题解释完整性、触发器、事务、并发和恢复

设计题通常只要求 E-R、关系模式和 SQL，但真正的数据库系统还要能正确运行。这里把后半课程也接上。

### 7.1 完整性约束

本题可定义的约束：

```text
实体完整性：
Publisher.PubID、Book.BookID、BookCopy.CopyID、Reader.ReaderID、Borrow.BorrowID 非空且唯一。

参照完整性：
Book.PubID 必须引用 Publisher。
BookCopy.BookID 必须引用 Book。
Borrow.ReaderID 必须引用 Reader。
Borrow.CopyID 必须引用 BookCopy。

用户定义完整性：
Reader.MaxBorrow >= 0。
Borrow.DueDate >= Borrow.BorrowDate。
Borrow.ReturnDate 可以为空，表示尚未归还。
BookCopy.Status 只能取 '在馆'、'借出'、'遗失' 等。
```

### 7.2 触发器：限制读者借书数量

题面说每位读者有可借阅图书数量限制。这个业务规则可用触发器实现。

示例逻辑：

```sql
CREATE TRIGGER Check_Borrow_Limit
BEFORE INSERT ON Borrow
FOR EACH ROW
BEGIN
  IF (
    SELECT COUNT(*)
    FROM Borrow
    WHERE ReaderID = NEW.ReaderID
      AND ReturnDate IS NULL
  ) >= (
    SELECT MaxBorrow
    FROM Reader
    WHERE ReaderID = NEW.ReaderID
  ) THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = '超过读者可借阅图书数量限制';
  END IF;
END;
```

课程联系：

- 触发器是事件驱动的特殊过程。
- 它用于实现复杂完整性约束。
- 触发器不是用 `EXECUTE` 调用，而是在插入/更新/删除事件发生时自动执行。

### 7.3 事务：借书操作必须是一个整体

借书不是单条更新就结束，至少包括：

1. 插入 Borrow 记录。
2. 修改 BookCopy 状态为“借出”。
3. 检查读者借书数量限制。

这些操作必须放在一个事务中：

```sql
BEGIN TRANSACTION;

INSERT INTO Borrow(BorrowID, ReaderID, CopyID, BorrowDate, DueDate, ReturnDate)
VALUES ('BR001', 'R001', 'C001', CURRENT_DATE, CURRENT_DATE + INTERVAL '30' DAY, NULL);

UPDATE BookCopy
SET Status = '借出'
WHERE CopyID = 'C001';

COMMIT;
```

如果第二步失败而第一步成功，就会出现“借阅记录显示已借出，但副本状态仍在馆”的不一致。所以要用事务保证 ACID：

- 原子性：两步要么都做，要么都不做。
- 一致性：借阅记录和副本状态一致。
- 隔离性：并发借书互不干扰。
- 持久性：提交后结果永久保存。

### 7.4 并发控制：防止两个人同时借同一本副本

并发场景：

```text
T1 查询 C001 在馆
T2 查询 C001 在馆
T1 插入借阅记录并更新 C001 为借出
T2 也插入借阅记录并更新 C001 为借出
```

结果：同一本副本被两个人借走，破坏一致性。

解决思路：

- 在更新副本状态前对该副本加 X 锁。
- 或用事务隔离级别和唯一约束控制。
- 遵守两段锁协议，保证并发调度可串行化。

封锁知识点：

- S 锁：读锁，其他事务可读不可写。
- X 锁：写锁，其他事务不能再读写。
- 两段锁：先申请锁，释放后不能再申请新锁。
- 多粒度封锁：可按数据库、表、元组等粒度加锁。

### 7.5 恢复：系统故障后怎么保证数据正确

假设借书事务提交前系统崩溃：

- 插入 Borrow 已写入缓冲区。
- BookCopy 状态更新未完成。

恢复系统根据日志处理：

- 未提交事务：UNDO。
- 已提交事务：REDO。

这对应恢复章节：

- 日志文件记录更新前旧值和更新后新值。
- 登记日志原则：先写日志，后写数据库。
- 检查点可减少恢复扫描范围。
- 数据库镜像可提高介质故障恢复速度。

## 8. 用本题解释安全性和外模式

图书馆系统中，不同用户权限不同：

```text
读者：只能查看可借书籍、本人借阅记录。
馆员：可办理借还书。
管理员：可维护书籍、出版社、读者信息。
```

这体现数据库安全性：

- 防止非法用户访问。
- 防止合法用户越权访问。

可用视图实现外模式：

```sql
CREATE VIEW ReaderBorrowView AS
SELECT R.ReaderID, R.ReaderName, B.Title, Bo.BorrowDate, Bo.DueDate, Bo.ReturnDate
FROM Reader R
JOIN Borrow Bo ON R.ReaderID = Bo.ReaderID
JOIN BookCopy C ON Bo.CopyID = C.CopyID
JOIN Book B ON C.BookID = B.BookID;
```

再授权：

```sql
GRANT SELECT ON ReaderBorrowView TO reader_role;
GRANT SELECT, INSERT, UPDATE ON Borrow TO librarian_role;
```

课程联系：

- 外模式是用户看到的局部数据视图。
- 视图能提供一定安全保护。
- `GRANT/REVOKE` 实现自主存取控制。
- 强制存取控制 MAC 还涉及主体许可证级别和客体密级。

## 9. 用本题解释物理设计、索引和查询优化

题目没有直接问物理设计，但实际系统需要考虑性能。

### 9.1 适合建立索引的列

```text
Book(PubID)             -- 查询某出版社书籍
Book(Author)            -- 查询某作者书籍
BookCopy(BookID)        -- 书籍到副本连接
Borrow(ReaderID)        -- 查询读者借阅记录
Borrow(CopyID)          -- 查询副本借阅历史
Borrow(DueDate)         -- 查询到期图书
Publisher(City)         -- 查询北京出版社
```

索引知识点：

- 经常查询、连接、排序的列适合建索引。
- 重复值很多或经常更新的列不适合建索引。
- 一个表最多一个聚集索引。

### 9.2 查询优化怎么发生

以到期图书查询为例：

低效思路：

```text
先把 Borrow、Reader、BookCopy、Book 做大连接，
再筛选 ReturnDate IS NULL 且 DueDate < CURRENT_DATE。
```

优化思路：

```text
先利用 Borrow(DueDate) 或 Borrow(ReturnDate, DueDate) 找到到期未还记录，
再连接 Reader、BookCopy、Book。
```

课程联系：

- 查询处理步骤：分析、检查、内部表示、优化、执行。
- 代数优化：选择下推、投影下推。
- 物理优化：选择索引扫描、连接算法。
- 集中式数据库优化重点通常是 I/O 代价。

## 11. 考试可直接写的精简答案

### 11.1 E-R 图文字答案

实体及属性：

```text
Publisher(PubID, PubName, Address, City)
Book(BookID, Title, Author, PubYear)
BookCopy(CopyID, Status, InDate)
Reader(ReaderID, ReaderName, Email, MaxBorrow)
Borrow(BorrowID, BorrowDate, DueDate, ReturnDate)
```

联系：

```text
Publisher 与 Book 为 1:n 出版联系。
Book 与 BookCopy 为 1:n 馆藏联系。
Reader 与 BookCopy 通过 Borrow 构成 m:n 借阅联系，联系属性为 BorrowDate、DueDate、ReturnDate。
```

### 11.2 关系模型答案

```text
Publisher(PubID, PubName, Address, City)
主码：PubID

Book(BookID, Title, Author, PubYear, PubID)
主码：BookID
外码：PubID -> Publisher(PubID)

BookCopy(CopyID, BookID, Status, InDate)
主码：CopyID
外码：BookID -> Book(BookID)

Reader(ReaderID, ReaderName, Email, MaxBorrow)
主码：ReaderID

Borrow(BorrowID, ReaderID, CopyID, BorrowDate, DueDate, ReturnDate)
主码：BorrowID
外码：ReaderID -> Reader(ReaderID)
外码：CopyID -> BookCopy(CopyID)
```

这组关系中非主属性均直接依赖于各自主码，不存在非主属性对码的部分依赖和传递依赖，符合 3NF。

### 11.3 创建书籍表和读者表

```sql
CREATE TABLE Book (
  BookID CHAR(20) PRIMARY KEY,
  Title VARCHAR(200) NOT NULL,
  Author VARCHAR(100),
  PubYear INT,
  PubID CHAR(10),
  FOREIGN KEY (PubID) REFERENCES Publisher(PubID)
);

CREATE TABLE Reader (
  ReaderID CHAR(20) PRIMARY KEY,
  ReaderName VARCHAR(80) NOT NULL,
  Email VARCHAR(120),
  MaxBorrow INT NOT NULL CHECK (MaxBorrow >= 0)
);
```

### 11.4 北京出版社书籍视图

```sql
CREATE VIEW BeijingPublisherBooks AS
SELECT B.BookID, B.Title, B.Author, B.PubYear,
       P.PubName, P.Address, P.City
FROM Book B
JOIN Publisher P ON B.PubID = P.PubID
WHERE P.City = '北京';
```

## 12. 答这种设计题的通用策略

1. 先找实体：名词通常是实体候选。
2. 再找联系：动词或业务关系通常是联系。
3. 看数量约束：判断 1:1、1:n、m:n。
4. 看查询需求：反推必须保存的属性。
5. 转关系模型：实体建表，1:n 在 n 端加外码，m:n 建中间表。
6. 标主码外码：主码保证实体完整性，外码保证参照完整性。
7. 检查 3NF：每个非主属性应直接依赖本表主码。
8. 写 SQL：建表先主表后从表；视图用 `CREATE VIEW AS SELECT`。
9. 补充约束：`NOT NULL`、`CHECK`、`FOREIGN KEY`、触发器。
10. 遇到“所有/全部”查询，想到关系代数除法、`NOT EXISTS` 或 `GROUP BY HAVING`。
