## 1. 数据库系统基础

### 1.1 必背概念

- <span style="color:red">数据库 DB</span>：长期存储在计算机内、有组织、可共享的数据集合。特点：长期存储、有组织、可共享、冗余较小、独立性较高、易扩展。
- <span style="color:red">数据库管理系统 DBMS</span>：位于用户与操作系统之间的数据管理软件。
- <span style="color:red">数据库系统 DBS</span>：引入数据库后的计算机系统，通常由数据库、DBMS 及开发工具、应用系统、数据库管理员和用户等组成。2019 填空也可概括为硬件、软件、人员。
- 数据管理发展阶段：<span style="color:red">人工管理阶段、文件系统阶段、数据库系统阶段</span>。

### 1.2 DBMS 主要功能

【填/简】

1. 数据定义功能：定义模式、外模式、内模式，定义表、视图、索引等。
2. 数据操纵功能：查询、插入、修改、删除。
3. 数据库运行管理/保护功能：安全性、完整性、并发控制、恢复。
4. 数据库建立和维护功能：装入、转储、重组、恢复、统计、性能监控。
5. 通信和数据转换：不同 DBMS、异构数据库互访互操作。

### 1.3 三级模式与两级映像

<span style="color:red">A 级重点：【填/判/选/简】</span>

| 层次 | 也称 | 含义 | 数量 |
|---|---|---|---|
| 外模式 | 子模式、用户模式 | 用户看到的局部数据逻辑结构，是安全保护的一种手段 | 可多个 |
| 模式 | 逻辑模式、概念模式 | 全体数据的逻辑结构和特征，是所有用户的公共数据视图 | 只有一个 |
| 内模式 | 存储模式 | 数据物理结构和存储方式 | 只有一个 |

两级映像：

- <span style="color:red">外模式/模式映像 -> 逻辑独立性</span>：模式改变时，修改映像可使外模式和应用程序不变。
- <span style="color:red">模式/内模式映像 -> 物理独立性</span>：存储结构改变时，修改映像可使模式和应用程序不变。

易错判断：

- “数据库逻辑独立性源于模式/内模式映像”是错的，应为外模式/模式映像。
- “当存储结构改变而逻辑结构不变，称为物理独立性”是对的。

### 1.4 数据模型三要素

<span style="color:red">A 级重点：【填】</span>

数据模型 = <span style="color:red">数据结构、数据操作、数据完整性约束</span>。

- 数据结构：静态特征，描述对象类型及联系，是数据模型最重要部分。
- 数据操作：动态特征，描述允许执行的操作及规则。
- 完整性约束：数据及联系必须满足的制约和依存规则。

## 2. 数据模型与 E-R 模型

### 2.1 概念模型和逻辑模型

【选/判】

- 概念模型也称信息模型，按用户观点建模，<span style="color:red">独立于计算机/DBMS</span>，典型表示方法是 E-R 模型。
- 逻辑模型包括层次模型、网状模型、关系模型、面向对象模型等。
- 层次模型用树结构表示，只能自然表达 1:n 联系。
- 网状模型允许一个结点有多个双亲，可表达复杂联系，但结构和语言复杂。
- 关系模型唯一的数据结构是<span style="color:red">关系/二维表</span>。

### 2.2 E-R 基本概念

<span style="color:red">A 级重点：【填/简/设计】</span>

- 实体：客观存在且可相互区别的事物。
- 属性：实体具有的某一特性。
- 码：能唯一标识实体的属性或属性组。
- 域：属性取值范围。
- 实体型：实体名及其属性集合。
- 实体集：同型实体的集合。
- 联系：实体内部或实体之间的关联。

E-R 图表示：

- 矩形：实体型。
- 椭圆：属性。
- 菱形：联系。
- 边旁标注：1:1、1:n、m:n。

### 2.3 E-R 到关系模型转换规则

<span style="color:red">A 级重点：【简/设计】</span>

1. 实体型转换为关系模式：实体属性作为关系属性，实体码作为主码。
2. 1:1 联系：可并入任一端实体关系，也可单独建关系；并入时加入对方码和联系属性。
3. 1:n 联系：通常并入 n 端实体关系，在 n 端加入 1 端主码作为外码，并加入联系属性。
4. m:n 联系：<span style="color:red">必须转换为一个独立关系模式</span>，各实体主码作为外码，联系属性也进入该关系；主码通常为各实体主码组合。
5. 多元联系：转换为独立关系模式，参与实体主码加联系属性组成关系，主码按语义确定，常为多个实体码组合。
6. 弱实体：通常把所属强实体的主码加入弱实体关系，和弱实体局部码共同构成主码。

易错点：

- “ER 图转换成关系模型是在概念设计阶段完成”是错的，属于<span style="color:red">逻辑结构设计阶段</span>。
- m:n 联系转换后的关系主键不是任一端的键，而通常是两端实体键的组合。

## 3. 关系模型与关系代数

### 3.1 关系模型基本概念

【填/判/选】

- 关系：二维表。
- 元组：表中的一行。
- 属性：表中的一列。
- 域：属性取值集合。
- 目或度：属性个数。
- 基数：元组个数。
- 候选码：能唯一标识元组的最小属性组。
- 主码：选定的候选码。
- 主属性：包含在任一候选码中的属性。
- 外码：一个关系中的属性或属性组引用另一个关系的主码。

关系性质：

- 列同质，每列来自同一域。
- 不允许重复元组。
- 元组次序无关。
- 属性次序理论上无关，但元组各分量与属性名对应。
- 每个属性值原子，不可再分。

### 3.2 三类完整性约束

<span style="color:red">A 级重点：【填/判/选】</span>

1. 实体完整性：主属性不能为空。
2. 参照完整性：外码要么为空，要么等于被参照关系中某个主码值。
3. 用户定义完整性：具体应用语义约束，如成绩范围、年龄范围。

任何关系模型必须满足：<span style="color:red">实体完整性和参照完整性</span>。

参照完整性违约处理：

- 拒绝执行（NO ACTION/RESTRICT）。
- 级联操作（CASCADE）。
- 设置为空值（SET NULL）。

### 3.3 关系代数基本运算

<span style="color:red">A 级重点：【填/选/综合】</span>

五种基本运算：<span style="color:red">并、差、笛卡尔积、选择、投影</span>。其他运算可由基本运算表达。

| 运算 | 符号 | 考点 |
|---|---|---|
| 选择 | σ | 从行角度选元组 |
| 投影 | Π | 从列角度选属性，结果会去重，元组数小于或等于原关系 |
| 并/差/交 | ∪、-、∩ | 要求关系兼容 |
| 笛卡尔积 | × | 若 R 有 m 个元组、S 有 n 个元组，结果 m×n 个元组 |
| 连接 | ⋈ | 条件连接 = 选择 + 笛卡尔积 |
| 自然连接 | ⋈ | 特殊等值连接，去掉重复属性列 |
| 外连接 | 左/右/全外连接 | 保留不满足连接条件的元组，用 NULL 补齐 |
| 除 | ÷ | “至少选修了全部课程”类查询 |

常考判断：

- “只从行角度进行运算”是选择。
- 自然连接会去掉重复属性列。
- 全外连接保留左右两边不满足连接条件的元组。

### 3.4 关系代数表达式模板

【综合】

查询 2000 年以后入职 design 部门且职称为 engineer 的员工姓名，   若有：

`S(Sno,Sname,Sage,Stitle)`、`D(Dno,Dname,Sno)`、`W(Sno,Dno,Year,Salary)`

可写：

```text
Π_Sname(
  σ_Year>2000 ∧ Dname='design' ∧ Stitle='engineer'
  (S ⋈ W ⋈ D)
)
```

优化思路：

```text
Π_Sname(
  (Π_Sno,Sname(σ_Stitle='engineer'(S)))
  ⋈
  (Π_Sno,Dno(σ_Year>2000(W)))
  ⋈
  (Π_Dno(σ_Dname='design'(D)))
)
```

核心原则：<span style="color:red">选择先做，投影尽量提前，把选择和笛卡尔积合并成连接，减少中间结果</span>。

## 4. SQL 高频内容

### 4.1 SQL 特点和使用方式

【填/选】

- 特点：综合统一、高度非过程化、面向集合、同一种语法可交互和嵌入使用。
- 使用方式：<span style="color:red">交互式 SQL 和嵌入式 SQL</span>。
- 嵌入式 SQL 使用游标协调 SQL 面向集合与宿主语言面向记录的处理方式。

### 4.2 SELECT 查询固定模板

<span style="color:red">A 级重点：【综合】</span>

```sql
SELECT [DISTINCT] 列名
FROM 表名或连接
WHERE 行条件
GROUP BY 分组列
HAVING 分组条件
ORDER BY 排序列 ASC/DESC;
```

易错点：

- `DISTINCT` 去重。
- `WHERE` 先筛记录，`HAVING` 后筛分组；两者都有时：<span style="color:red">先 WHERE，再 GROUP BY，再 HAVING</span>。
- `COUNT(*)` 不忽略 NULL；`SUM(列)`、`AVG(列)`、`MAX(列)`、`MIN(列)` 忽略 NULL。

### 4.3 高频 SQL 例题模板

学生、课程、选课：

```sql
-- 查询年龄大于 20 的学生姓名、年龄、性别
SELECT 姓名, 年龄, 性别
FROM 学生表
WHERE 年龄 > 20;

-- 查询选修了“数据库原理”的学生姓名
SELECT DISTINCT S.姓名
FROM 学生表 S
JOIN 学生选课表 SC ON S.学号 = SC.学号
JOIN 课程表 C ON SC.课程号 = C.课程号
WHERE C.课程名 = '数据库原理';

-- 查询至少选修两门课的学生姓名
SELECT S.姓名
FROM 学生表 S
JOIN 学生选课表 SC ON S.学号 = SC.学号
GROUP BY S.学号, S.姓名
HAVING COUNT(*) >= 2;
```

员工、部门、工作：

```sql
-- 年龄超过 60 岁的员工
SELECT Sname, Sage, Stitle
FROM S
WHERE Sage > 60;

-- 工资超过 5000 的员工姓名
SELECT DISTINCT S.Sname
FROM S
JOIN W ON S.Sno = W.Sno
WHERE W.Salary > 5000;

-- 平均年龄超过 50 的部门编号、部门名称、平均年龄
SELECT D.Dno, D.Dname, AVG(S.Sage) AS AvgAge
FROM D
JOIN W ON D.Dno = W.Dno
JOIN S ON W.Sno = S.Sno
GROUP BY D.Dno, D.Dname
HAVING AVG(S.Sage) > 50;
```

### 4.4 表、视图、索引、授权

【填/选/设计】

```sql
CREATE TABLE 表名 (
  列名 数据类型 [列级约束],
  ...
  PRIMARY KEY (列名),
  FOREIGN KEY (列名) REFERENCES 被参照表(主码列)
);

CREATE VIEW 视图名 AS
SELECT ...
FROM ...
WHERE ...;

GRANT SELECT, UPDATE ON 表名 TO 用户名 [WITH GRANT OPTION];
REVOKE SELECT ON 表名 FROM 用户名;
```

重点：

- `WITH GRANT OPTION` 表示允许用户把获得的权限再转授给别人。
- 自主存取控制 DAC 主要通过 `GRANT` 和 `REVOKE` 实现。
- 视图是外模式的一种实现方式，可简化查询、保证一定安全性、提高逻辑独立性，但一般不保存中间结果数据。
- 删除基本表后，依赖该表的视图通常不能正常使用。

索引：

- 经常查询的列、连接列、主键/外键、`ORDER BY` 常用列适合建索引。
- 重复值很多、经常更新的列不适合建索引。
- 一个基本表最多只能有一个聚集索引。

## 5. 查询处理与查询优化

### 5.1 查询处理步骤

【简/选】

1. 查询分析：词法、语法分析。
2. 查询检查：语义检查、权限检查、完整性检查。
3. 建立查询内部表示：通常转换为关系代数表达式或查询树。
4. 查询优化：选择高效执行策略。
5. 生成执行计划并执行。

### 5.2 查询优化重点

<span style="color:red">A/B 级重点：【填/选/综合】</span>

- 大型集中式关系数据库，优化重点是使<span style="color:red">访问外存储器的 I/O 代价</span>最小。
- 分布式数据库还要重点考虑通信代价。
- 代数优化：通过等价变换减少中间结果。
- 物理优化：选择存取路径和底层操作算法。

启发式规则：

1. <span style="color:red">选择尽可能先做</span>。
2. 投影尽可能提前。
3. 把选择与笛卡尔积合并为连接。
4. 连接顺序优先让小关系、选择率低的关系先参与。
5. 公共子表达式可复用。

### 5.3 选择和连接实现方法

【填/选】

选择操作：

- 小关系：顺序扫描法。
- 主码等值查询：主码索引。
- 选择率低且有索引：索引扫描。
- OR 条件通常可能全表扫描。

连接操作：

- 嵌套循环法。
- 排序合并法。
- 索引连接法。
- 散列连接法。

常考填空：连接运算主要实现方法包括<span style="color:red">嵌套循环法、排序合并法、索引连接法、散列连接法</span>。

## 6. 数据库安全性

### 6.1 安全性与完整性的区别

<span style="color:red">A 级重点：【填/判/选】</span>

- 数据库完整性：防止数据库中存在不符合语义、不正确的数据。
- 数据库安全性：保护数据库，防止恶意破坏和非法存取。

### 6.2 安全控制方法

【填/选】

1. 用户身份鉴别。
2. 存取控制。
3. 视图机制。
4. 审计。
5. 数据加密。

自主存取控制 DAC：

- 用户对不同数据库对象有不同权限。
- SQL 中主要通过 `GRANT` 和 `REVOKE` 实现。

强制存取控制 MAC：

- 主体：用户或进程，有许可证级别。
- 客体：数据对象，有密级。
- 读规则：仅当<span style="color:red">主体许可证级别不低于客体密级</span>时，主体才能读客体。
- 写规则：通常要求主体许可证级别不高于客体密级，以防高密级信息向低密级泄露。

安全级别：

- 数据库产品安全级别题中，若问“真正意义上的安全产品至少要求达到/最低安全级别”，按教材常考答案选 **C2 级**。
- B1 级开始支持强制存取控制，安全要求高于 C2，但不是这两套卷选择题的“最低”答案。

审计：

- DBMS 自动把用户对数据库的操作记录到审计日志中，用于安全性检查和追踪。

## 7. 数据库完整性与触发器

### 7.1 完整性机制

【填/简】

DBMS 为维护完整性必须提供：

1. 定义完整性约束条件的机制。
2. 完整性检查方法。
3. 违约处理机制。

### 7.2 触发器

<span style="color:red">A 级重点：【填/判/选/综合】</span>

定义：触发器是用户定义在关系表上的一类<span style="color:red">由事件驱动、由服务器自动激活</span>的特殊过程，常用于实现复杂完整性约束。

常见语法：

```sql
CREATE TRIGGER 触发器名
BEFORE|AFTER INSERT|DELETE|UPDATE ON 表名
FOR EACH ROW|STATEMENT
[WHEN 条件]
BEGIN
  触发动作;
END;
```

考点：

- 触发器不是由 `EXECUTE` 手工调用，而是由事件自动触发。
- 行级触发器每影响一行执行一次；语句级触发器每条 SQL 执行一次。
- 执行顺序通常为 BEFORE 触发器 -> 触发 SQL -> AFTER 触发器。

设计题模板：更新部门主管时，新主管必须存在于员工表。

```sql
CREATE TRIGGER Check_Manager
BEFORE UPDATE OF Sno ON D
FOR EACH ROW
BEGIN
  IF NOT EXISTS (SELECT 1 FROM S WHERE S.Sno = NEW.Sno) THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '主管必须是员工表中的员工';
  END IF;
END;
```

不同 DBMS 的触发器语法略有差异，考试重点是能表达“触发事件、检查条件、违约处理”。

## 8. 事务、恢复与日志

### 8.1 事务与 ACID

<span style="color:red">A 级重点：【填/选/简】</span>

事务：用户定义的一个数据库操作序列，是不可分割的工作单位，也是恢复和并发控制的基本单位。

ACID：

- 原子性 Atomicity：事务操作要么全做，要么全不做。
- 一致性 Consistency：事务执行前后数据库保持一致状态。
- 隔离性 Isolation：并发事务之间互不干扰。
- 持久性 Durability：事务一旦提交，对数据库的更新永久保存。

```sql
BEGIN TRANSACTION;
...
COMMIT;   -- 提交
ROLLBACK; -- 回滚
```

### 8.2 故障类型与恢复策略

【填/选/简】

| 故障 | 含义 | 恢复 |
|---|---|---|
| 事务故障 | 事务非预期终止，如死锁、溢出、违反完整性 | UNDO 该事务 |
| 系统故障 | 系统停止，内存丢失，数据库本身未破坏 | UNDO 未提交，REDO 已提交 |
| 介质故障 | 外存损坏，数据库被破坏 | 重装后备副本，再 REDO 成功事务 |
| 病毒/人为破坏 | 恶意破坏 | 依靠备份、日志、安全机制 |

<span style="color:red">系统故障恢复：已提交事务 REDO，未提交事务 UNDO。</span>

### 8.3 日志

【填/简】

日志文件记录事务对数据库的更新操作。作用：

1. 事务故障恢复。
2. 系统故障恢复。
3. 配合后备副本进行介质故障恢复。

登记日志原则：<span style="color:red">先写日志，后写数据库</span>。

以记录为单位的日志通常包含：

- 事务标识。
- 操作类型：插入、删除、修改。
- 操作对象。
- 更新前旧值。
- 更新后新值。

### 8.4 检查点恢复

<span style="color:red">A 级重点：【选/简】</span>

检查点用于减少恢复时扫描日志和 REDO 的工作量。

具有检查点的恢复规则：

- 检查点前已经提交的事务通常无需 REDO。
- 检查点前开始、检查点后故障前提交的事务：REDO。
- 检查点后开始、故障前提交的事务：REDO。
- 故障时未完成的事务：UNDO。

2019 题型模板：

T1 检查点前提交；T2 检查点前开始、故障前提交；T3 检查点前开始、故障时未完成；T4 检查点后开始、故障前提交；T5 检查点后开始、故障时未完成。

- REDO：T2、T4。
- UNDO：T3、T5。
- T1：无需处理或无需 REDO。

### 8.5 数据转储与数据库镜像

【简】

- 静态转储：无运行事务时转储，副本一致，实现简单但可用性差。
- 动态转储：转储与事务并发执行，需日志配合才能恢复到一致状态。
- 海量转储：每次转储全部数据库。
- 增量转储：只转储上次转储后变化的数据。

数据库镜像：

- DBMS 自动把整个数据库或关键数据复制到另一个磁盘，保持镜像与主库一致。
- 作用：介质故障时可快速切换和恢复；也可用于读操作分担。
- 缺点：频繁复制会降低效率，通常只镜像关键数据和日志。

## 9. 并发控制

### 9.1 并发操作带来的问题

<span style="color:red">A 级重点：【填/选/简】</span>

1. 丢失修改：两个事务读同一数据并修改，一个事务的修改被另一个覆盖。
2. 不可重复读：事务两次读取同一数据，中间被其他事务修改/删除/插入，结果不一致。
3. 读脏数据：读到了另一个事务尚未提交的数据，而该事务后来回滚。

### 9.2 封锁与封锁协议

<span style="color:red">A 级重点：【选/判/填】</span>

基本锁：

- X 锁/排他锁/写锁：只允许加锁事务读写，其他事务不能再加任何锁。
- S 锁/共享锁/读锁：其他事务可再加 S 锁，但不能加 X 锁。

封锁协议：

| 协议 | 规则 | 解决问题 |
|---|---|---|
| 一级封锁协议 | 修改前加 X 锁，事务结束释放 | 防止丢失修改 |
| 二级封锁协议 | 一级 + 读前加 S 锁，读完释放 | 防止丢失修改、读脏数据 |
| 三级封锁协议 | 一级 + 读前加 S 锁，事务结束释放 | 防止丢失修改、读脏数据、不可重复读 |

### 9.3 活锁、死锁、可串行化

【简/综合】

- 活锁：某事务长期得不到锁。解决：先来先服务。
- 死锁：多个事务互相等待对方释放锁。预防：一次封锁法、顺序封锁法；诊断：超时法、等待图法；解除：撤销代价较小事务。

可串行化调度：

- 多个事务并发执行的结果与某一串行执行顺序结果相同，则该调度可串行化。
- 冲突操作：不同事务对同一数据的读写、写读、写写。
- 冲突可串行化：保持冲突操作次序不变，可交换非冲突操作得到串行调度。

### 9.4 两段锁协议 2PL

<span style="color:red">A 级重点：【选/判】</span>

两段锁协议要求事务分两个阶段：

1. 扩展阶段：可以申请获得锁，不能释放锁。
2. 收缩阶段：可以释放锁，不能再申请新锁。

结论：

- 遵守两段锁协议是可串行化调度的<span style="color:red">充分条件，不是必要条件</span>。
- 两段锁可能发生死锁。
- 违反判断方法：一旦出现 `Unlock` 后又出现新的 `Slock/Xlock`，即违反两段锁协议。

### 9.5 多粒度封锁与意向锁

<span style="color:red">A 级重点：【填/选】</span>

封锁粒度：

- 粒度大：锁少，开销小，并发度低。
- 粒度小：并发度高，开销大。

多粒度封锁中，为提高检查效率，引入<span style="color:red">意向锁</span>：

- IS：意向共享锁，后裔结点拟加 S 锁。
- IX：意向排他锁，后裔结点拟加 X 锁。
- SIX：共享意向排他锁，当前结点加 S 锁，并对后裔拟加 X 锁。

常考相容结论：

- 某结点已加 SIX 锁，其他事务通常还可加 IS 锁。
- SIX 与 S、X、IX 均不相容。

## 10. 关系数据库设计理论：函数依赖与范式

### 10.1 函数依赖基本概念

<span style="color:red">A 级重点：【填/选/综合】</span>

在关系模式 R(U) 中，若任意两个元组 X 属性值相等时，Y 属性值也相等，则称 X 函数决定 Y，记作 `X -> Y`。

- 平凡函数依赖：`Y ⊆ X`。
- 非平凡函数依赖：`Y` 不包含于 `X`。
- 完全函数依赖：`X -> Y` 成立且 X 的任何真子集都不能决定 Y。
- 部分函数依赖：X 的某个真子集可决定 Y。
- 传递函数依赖：`X -> Y`，`Y -> Z`，且 `Y` 不决定 `X`，则 `X -> Z` 为传递依赖。

### 10.2 闭包与候选码计算

<span style="color:red">A 级重点：【综合】</span>

属性闭包 `X+` 计算步骤：

1. 初始 `X+ = X`。
2. 若有函数依赖 `Y -> Z`，且 `Y ⊆ X+`，则把 `Z` 加入 `X+`。
3. 重复直到不再增加属性。
4. 若 `X+ = U`，则 X 是超码；若 X 的任一真子集都不是超码，则 X 是候选码。

例 1：2011 综合题  
R(A,B,D,E,H)，F={A->D, AB->DE, E->H}

- `(AB)+ = AB`
- A->D，得 `ABD`
- AB->DE，得 `ABDE`
- E->H，得 `ABDEH`
- 覆盖全部属性，所以 AB 是候选码。A+ = AD，B+ = B，均不能覆盖全部属性，AB 最小。

例 2：2019 综合题  
R(A,B,C,D,E)，F={AB->C, B->D, C->E, EC->B}

- `(AB)+`：AB -> C，得 ABC；B -> D，得 ABCD；C -> E，得 ABCDE，所以 AB 是候选码。
- `(AC)+`：C -> E，得 ACE；EC -> B，得 ABCE；B -> D，得 ABCDE，所以 AC 也是候选码。
- 这类题要先找“不在任何依赖右部出现的属性”，它们必须在候选码中。

### 10.3 Armstrong 公理与常用推理

【综合/证明】

基本公理：

1. 自反律：若 `Y ⊆ X`，则 `X -> Y`。
2. 增广律：若 `X -> Y`，则 `XZ -> YZ`。
3. 传递律：若 `X -> Y` 且 `Y -> Z`，则 `X -> Z`。

常用推论：

- 合成：`X -> Y` 且 `X -> Z`，则 `X -> YZ`。
- 分解：`X -> YZ`，则 `X -> Y` 且 `X -> Z`。
- 伪传递：`X -> Y` 且 `YZ -> W`，则 `XZ -> W`。

证明模板：证明 `X->Y, YZ->W => XZ->W`

```text
由 X->Y，根据增广律得 XZ->YZ；
又已知 YZ->W；
根据传递律，得 XZ->W。
```

### 10.4 范式

<span style="color:red">A 级重点：【填/判/选/综合】</span>

| 范式 | 判定条件 | 消除的问题 |
|---|---|---|
| 1NF | 每个属性不可再分 | 非原子属性 |
| 2NF | 1NF 且非主属性完全依赖于每个候选码 | 非主属性对码的部分依赖 |
| 3NF | 2NF 且非主属性不传递依赖于候选码 | 非主属性传递依赖 |
| BCNF | 每个非平凡函数依赖 X->Y 的 X 都是候选码/超码 | 主属性间依赖等更强异常 |
| 4NF | 每个非平凡多值依赖 X ->-> Y 的 X 都含有候选码 | 非平凡多值依赖 |

重要结论：

- BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF。
- R 属于 3NF，则一定属于 2NF。
- 任意二元关系模式若属于 3NF，则必定属于 BCNF。
- 规范化程度越高，不代表操作效率一定越高；可能需要更多连接，查询效率下降。
- 规范化是为了减少冗余和异常，实际设计需兼顾性能。

### 10.5 最高范式判定步骤

【综合】

1. 求候选码，确定主属性和非主属性。
2. 看是否 1NF：关系数据库默认满足。
3. 看 2NF：非主属性是否部分依赖于候选码。
4. 看 3NF：非主属性是否传递依赖于候选码。
5. 看 BCNF：每个非平凡依赖的左部是否都是超码。

例：R(S,D,M)，F={S->D, D->M}

- S+ = SDM，所以 S 是候选码，S 为主属性，D、M 为非主属性。
- S->D，D->M，所以 S->M 是传递依赖。
- R 达到 2NF，但不达到 3NF。

### 10.6 模式分解

【选/综合】

分解目标：

- 无损连接：分解后自然连接能恢复原关系，不产生伪元组。
- 保持函数依赖：原函数依赖可在各子模式上检查，不必连接后再检查。

二元分解无损判定常用条件：

对 R 分解为 R1、R2，若 `(R1 ∩ R2) -> R1` 或 `(R1 ∩ R2) -> R2`，则无损连接。

2019 选择题思路：

R(A,B,C)，F={A->B, B->C}，分解为 R1(A,B)、R2(A,C)。

- 交集为 A，A->AB，故无损。
- 依赖 B->C 无法在 R1 或 R2 单独保持，故不保持函数依赖。

## 12. 近三套卷大题模板

### 12.1 医院/门诊/病房类设计题

<span style="color:red">A 级重点：【设计】</span>

这类题本质是“科室-医生-患者-就诊/病床/药品”的 E-R 设计。

常见实体：

- 科室(科室号, 科室名, 位置, 电话)
- 医生(医生号, 姓名, 职称, 科室号)
- 患者(患者号, 姓名, 性别, 年龄, 联系方式)
- 药品(药品号, 药品名, 规格, 单价)
- 病房(病房号, 房间号, 科室号)
- 病床(床号, 病房号)

常见联系：

- 科室 1:n 医生：医生只属于一个科室。
- 科室 1:n 病房：病房只属于一个科室。
- 病房 1:n 病床。
- 患者 m:n 医生，通过“就诊/诊疗”联系，记录就诊时间、诊断意见。
- 就诊 m:n 药品，通过“用药明细”联系，记录药品数量。
- 病人占用病床要带时间属性，因病床会轮转，通常建“住院/占床”关系，含开始时间、结束时间。

门诊管理示例关系模式：

```text
Department(DeptID, DeptName, Location, Phone)
Doctor(DoctorID, DoctorName, Title, DeptID)
Patient(PatientID, PatientName, Gender, Age, Phone)
Medicine(MedID, MedName, Spec, Price)
Visit(VisitID, PatientID, DoctorID, VisitTime, Diagnosis)
VisitMedicine(VisitID, MedID, Quantity)
```

主码：

- Department: DeptID
- Doctor: DoctorID
- Patient: PatientID
- Medicine: MedID
- Visit: VisitID
- VisitMedicine: (VisitID, MedID)

外码：

- Doctor.DeptID -> Department.DeptID
- Visit.PatientID -> Patient.PatientID
- Visit.DoctorID -> Doctor.DoctorID
- VisitMedicine.VisitID -> Visit.VisitID
- VisitMedicine.MedID -> Medicine.MedID

查看曾到骨科就诊过的患者基本信息：

```sql
CREATE VIEW OrthopedicsPatients AS
SELECT DISTINCT P.PatientID, P.PatientName, P.Gender, P.Age, P.Phone
FROM Patient P
JOIN Visit V ON P.PatientID = V.PatientID
JOIN Doctor Doc ON V.DoctorID = Doc.DoctorID
JOIN Department D ON Doc.DeptID = D.DeptID
WHERE D.DeptName = '骨科';
```

### 12.2 图书馆类设计题

<span style="color:red">A 级重点：【设计/SQL】</span>

常见实体：

- Publisher(PubID, PubName, Address, City)
- Book(BookID, Title, Author, PubID)
- Copy(CopyID, BookID, Status)
- Reader(ReaderID, ReaderName, Email, MaxBorrow)
- Borrow(ReaderID, CopyID, BorrowDate, DueDate, ReturnDate)

关系说明：

- 一个出版社出版多种书：Publisher 1:n Book。
- 同一书籍可馆藏多本：Book 1:n Copy。
- 读者可借多本书，书副本可被多个读者在不同时段借阅：Reader 和 Copy 通过 Borrow 形成带时间属性的联系。

创建书籍表、读者表示例：

```sql
CREATE TABLE Book (
  BookID CHAR(20) PRIMARY KEY,
  Title VARCHAR(100) NOT NULL,
  Author VARCHAR(60),
  PubID CHAR(20),
  FOREIGN KEY (PubID) REFERENCES Publisher(PubID)
);

CREATE TABLE Reader (
  ReaderID CHAR(20) PRIMARY KEY,
  ReaderName VARCHAR(60) NOT NULL,
  Email VARCHAR(100),
  MaxBorrow INT CHECK (MaxBorrow >= 0)
);
```

出版社在北京的所有书籍视图：

```sql
CREATE VIEW BeijingPublisherBooks AS
SELECT B.BookID, B.Title, B.Author, P.PubName
FROM Book B
JOIN Publisher P ON B.PubID = P.PubID
WHERE P.City = '北京';
```

查询到期图书名称和读者邮箱：

```sql
SELECT B.Title, R.Email
FROM Borrow Bo
JOIN Copy C ON Bo.CopyID = C.CopyID
JOIN Book B ON C.BookID = B.BookID
JOIN Reader R ON Bo.ReaderID = R.ReaderID
WHERE Bo.ReturnDate IS NULL
  AND Bo.DueDate < CURRENT_DATE;
```

### 12.3 函数依赖、候选码、范式题

【综合】

答题模板：

```text
1. 求候选码：
   先找未出现在任何依赖右部的属性，它们必须包含在候选码中。
   计算闭包，直到覆盖 U。

2. 判断范式：
   关系默认 1NF；
   若有非主属性对候选码部分依赖，则不满足 2NF；
   若有非主属性对候选码传递依赖，则不满足 3NF；
   若存在 X->Y 且 X 不是超码，则不满足 BCNF。

3. 写结论：
   “因此 R 最高属于 xNF，理由是……”
```

### 12.4 SQL 综合题

【综合】

答题模板：

1. 简单筛选：`SELECT 列 FROM 表 WHERE 条件`。
2. 多表查询：先确认连接路径，再 `JOIN ... ON ...`。
3. 分组统计：`GROUP BY` + `HAVING`。
4. 至少/全部：优先考虑 `GROUP BY HAVING COUNT` 或 `NOT EXISTS`。
5. 插入/更新/删除：写清字段和值，更新和删除必须有 `WHERE`。

图书借阅例：

```sql
-- 插入图书
INSERT INTO Book(Bno, Bname, Press, Price)
VALUES ('b010', 'Database', 'Elsvier', 99);

-- 修改读者 R001 在 2013-05-19 归还 b010
UPDATE Borrow
SET Rdate = DATE '2013-05-19'
WHERE Rno = 'R001' AND Bno = 'b010';

-- 统计每个读者未归还图书数量
SELECT Rno, COUNT(*) AS NotReturnedCount
FROM Borrow
WHERE Rdate IS NULL
GROUP BY Rno;
```

## 13. 选择/填空/判断速记清单

<span style="color:red">A 级速记</span>

- 数据管理三阶段：人工管理、文件系统、数据库系统。
- 数据模型三要素：数据结构、数据操作、完整性约束。
- DBMS 保护功能：安全性、完整性、并发控制、恢复。
- 三级模式：外模式、模式、内模式。
- 两级映像：外/模式保逻辑独立；模式/内保物理独立。
- 关系模型唯一数据结构：关系。
- 关系代数五个基本运算：并、差、笛卡尔积、选择、投影。
- SQL 两种使用方式：交互式、嵌入式。
- `GRANT/REVOKE`：自主存取控制。
- `WITH GRANT OPTION`：允许转授权。
- 完整性防错误数据；安全性防非法存取和破坏。
- 参照完整性删除策略：拒绝、级联、置空。
- 触发器：事件驱动、自动执行，不是 `EXECUTE` 调用。
- 事务 ACID：原子性、一致性、隔离性、持久性。
- 系统故障恢复：未提交 UNDO，已提交 REDO。
- 并发异常：丢失修改、不可重复读、读脏数据。
- 基本锁：S 锁、X 锁。
- 两段锁：释放锁后不能再申请锁。
- 意向锁：IS、IX、SIX。
- 1NF：属性不可再分；2NF：消除非主属性部分依赖；3NF：消除非主属性传递依赖；BCNF：每个决定因素都是超码。
- 数据库设计步骤：需求分析、概念设计、逻辑设计、物理设计、实施、运行维护。
- 分 E-R 图冲突：属性冲突、命名冲突、结构冲突。

**易错判断集中记**

- “合法用户可以操纵数据库中所有数据”错，合法用户也受权限限制。
- “所有视图都能像基本表一样更新”错，复杂视图不可更新。
- “一个表可有多个聚集索引”错，最多一个。
- “规范化程度越高，操作效率一定越高”错。
- “外键必须与被参照主键同名”错，只需域相同/类型兼容。
- “采用增量备份可不使用日志恢复”错，通常仍需日志。
- “关系中元组次序重要”错。
- “关系中属性值必须原子”对。
- “触发器由 EXECUTE 调用”错。

## 15. 考前答题提醒

- 设计题先画/写实体和联系，再写关系模式；不要一上来只写表。
- 主码用下划线或明确写 `主码：...`，外码写 `外码：... -> ...`。
- SQL 题多表查询一定写连接条件，避免笛卡尔积。
- 分组条件用 `HAVING`，普通行条件用 `WHERE`。
- 触发器题要写清触发事件、触发时机、检查条件、违约动作。
- 范式题不要只写结论，必须写候选码和违反哪个依赖。
- 恢复题先按是否提交分 REDO/UNDO，再看检查点前后。
- 两段锁题只看关键规则：第一次 `Unlock` 后不能再 `Lock`。
